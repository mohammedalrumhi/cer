# Certificate Generator — Agent Guide

This guide is written for AI coding agents. It describes the project architecture, conventions, build/test commands, and important implementation details as they actually exist in the repository.

---

## Project Overview

This is a **monorepo** for a certificate generation web app for an Arabic educational institution (`دار الإتقان العالي`).

- **Backend**: Node.js + Express API that stores templates, students, branding, and generates Arabic PDF certificates.
- **Frontend**: Vite + React single-page app, **Arabic only and right-to-left**, with a Canva-level template editor
  (the "studio"), a template gallery and a bulk-generation wizard.
- **Deployment model**: The backend serves the API and can also serve the built frontend from `frontend/dist`. This is the recommended setup for Hostinger and similar Node.js hosts.

The system is designed around **templates** that contain a background (solid color or image) and a list of **elements** (text, dynamic text, images, shapes). A certificate is generated by rendering a template once per student and substituting dynamic fields (`studentName`, `date`, `recitalType`, etc.).

## Technology Stack

### Backend

- **Runtime**: Node.js (uses `node --watch` in dev).
- **Framework**: Express 5.
- **PDF generation**: the shared scene renderer (`shared/render`, HarfBuzz WASM + bidi-js) painted by `pdfkit` as vector paths. The v1 `pdfkit` + `arabic-reshaper` text renderer is kept behind `PDF_ENGINE=legacy`.
- **Bulk jobs**: in-process queue (`services/jobs.js`) persisted as storage records; output files in `<DATA_DIR>/jobs`.
- **Images**: `pngjs` + `jpeg-js` decode images for the shared pixel filters; `fontkit` checks Arabic coverage of fonts; `qrcode-generator` builds QR codes (also in the frontend).
- **Database**: MySQL via `mysql2/promise`, or local JSON files when MySQL is not configured.
- **File uploads**: `multer` with custom file filters.
- **Testing**: Node.js built-in `node:test` + `supertest`.
- **Environment**: `dotenv` reads `.env` files at project root and inside `backend/`.

### Frontend

- **Bundler**: Vite 8.
- **Framework**: React 19, React Router 7.
- **Styling**: Tailwind CSS v4 (`@tailwindcss/vite`) with custom CSS in `frontend/src/index.css`.
- **Canvas editor**: React-Konva + Konva, state in a zustand store. Every op is painted by `editor/render/paintOps.js` (the canvas twin of the PDF painter); Konva only does hit testing and transforms.
- **UI primitives**: Radix (`@radix-ui/react-*`, with `DirectionProvider dir="rtl"`), `@dnd-kit` for panel drag-and-drop and layer sorting, self-hosted IBM Plex Sans Arabic, design tokens in `src/styles/tokens.css`.
- **HTTP client**: Axios with request/response interceptors for auth tokens.
- **Icons**: `lucide-react`.
- **Build output**: `frontend/dist`.

## Environment Variables

The backend reads from `.env` at the project root **and** `backend/.env`. The root `.env` also supplies `VITE_API_BASE` to the Vite dev server.

### Required / commonly used

| Variable | Purpose |
|----------|---------|
| `PORT` | Backend port (default `4000`). |
| `AUTH_TOKEN_SECRET` | HMAC secret used to sign login tokens. Must be long and random in production. |
| `VITE_API_BASE` | Frontend API base URL. Use `http://localhost:4000` locally, `/api` for same-domain production. |
| `PERSISTENT_STORAGE_DIR` | Writable folder for runtime data/uploads/fonts on production hosts. |
| `PUBLIC_BASE_URL` | Optional. Origin printed in verification QR codes (`<origin>/verify/<serial>`); defaults to the request origin. |

### MySQL connection (pick one style)

- `MYSQL_URL` or `DATABASE_URL`: full connection string.
- Or separate: `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD`.

If any MySQL variable is present, the app uses MySQL storage; otherwise it falls back to JSON files in `backend/data` and `backend/uploads`.

### Optional path overrides

- `DATA_DIR` — JSON data directory when using file storage.
- `UPLOADS_DIR` — uploaded images directory.
- `FONTS_DIR` — custom font directory.
- `FRONTEND_DIST_DIR` — custom path to built frontend; defaults to `frontend/dist`.

See `backend/.env.example` and `.env.example` for local-development templates.

## Build and Run Commands

All commands assume the working directory is the project root.

## Testing

```bash
npm test                 # everything below
npm run test:backend     # node:test (backend/test), in-memory storage, no database needed
npm run test:frontend    # Vitest: shared/**/*.test.js and frontend/src/**/*.test.js
npm run test:e2e         # Playwright, desktop + mobile projects (starts its own servers)
npm run test:visual      # editor-vs-PDF fidelity for every template and preset
```

- Playwright starts an isolated backend (`tests/support/start-test-backend.mjs`) on port 4310 with JSON
  storage on a temp copy of `backend/data`, and Vite on port 5310. Locally it uses the installed Chrome;
  in CI run `npx playwright install chromium` first.
- The fidelity suite must pass before any change to `shared/render`, `shared/assets`, `frontend/src/editor/render`
  (especially `paintOps.js`) or `backend/src/services/scenePdfRenderer.js` is committed: the painters must stay
  step-for-step identical. It covers stored templates, presets, every starter template and
  `tests/visual/fixtures/studioElements.js` (every element type and effect). Add new element types there.
- `tests/e2e/arabic-only.spec.js` fails on any Latin-letter UI word; only file formats, paper sizes and key names
  are allowed. Put new wording in `strings.ar.js`.
- The test backend caches the shared ESM modules: restart `tests/support/start-test-backend.mjs` after changing
  `shared/` when reusing servers.
- Useful scripts: `tests/support/screenshots.mjs` (light/dark screenshots), `tests/support/renderStarters.mjs`
  and `contactSheet.mjs` (review starter designs through the PDF renderer), `tests/support/rasterize.mjs`.

## Code Organization

### Backend

- **`server.js`**: loads `.env` files, initializes storage, creates the app, starts listening, and registers graceful shutdown.
- **`app.js`**: factory function `createApp({ storage })`. Wires middleware, static file serving, API routes, and SPA fallback. Exposes `/api/health`.
- **`routes/`**: each file exports a router factory (except `fonts.js`, which is a plain router). All data access goes through the `storage` object.
- **`services/pdfService.js`**: picks the renderer (`PDF_ENGINE`, default `scene`). `scenePdfRenderer.js` paints the shared scene and exposes `prepareTemplate` / `renderCertificatesDocument` (streaming, progress, cancel, 2-up); `legacyPdfRenderer.js` is the v1 renderer; `certificateData.js` only resolves image sources (field values come from `shared/model/fields.js`).
- **`services/jobs.js`**: bulk generation queue, serial issuing (`issueCertificates`) for verification.
- **Routes added by the studio**: `/api/assets` (uploads library), `/api/backgrounds` (frames + colour variants),
  `/api/templates/:id/versions[/:vid[/restore]]`, `/api/jobs` (create, poll, cancel, download, history),
  `/api/certificates/serials` (for browser-rendered images), public `/api/verify/:serial`.
  `PUT /api/templates/:id` accepts `baseVersion` and answers **409** when the stored `version` moved on.
- **`shared.js`**: loads the ESM `shared/` modules from CommonJS via dynamic `import()`.
- **`storage/withTemplateMigrations.js`**: wraps any storage so templates are migrated to the current schema on read and on write. Reads never rewrite stored data.
- **`storage/`**: three interchangeable implementations:
  - `fileStorage.js` — JSON files via `utils/fileDb.js`.
  - `mysqlStorage.js` — MySQL pool with automatic schema creation and seeding from JSON files.
  - `memoryStorage.js` — in-memory, used by tests and seed fixtures.
- **`utils/uploads.js`**: multer configurations for images, spreadsheets, and fonts.

### Frontend

- **`api/client.js`**: centralizes API calls, builds asset URLs, and handles the auth token in `localStorage`.
- **`App.jsx`**: routing and route guards (`ProtectedRoute`, `GuestRoute`). The template editor (`/templates/:id/edit`) is full-screen without the sidebar layout.
- **`pages/`**: route pages. `Generate.jsx` is for detailed templates; `GenerateSimple.jsx` is for quick name-only generation.
- **`editor/`**: the template editor.
  - `store/editorStore.js`: zustand store (document, selection, viewport, ui) with command history. Mutate through actions such as `updateElements` and `addElements`, pass a `coalesceKey` for typing, and use `beginTransaction`/`commitTransaction` for gestures.
  - `canvas/`: Konva stage, delegated drag and transform, the text edit overlay, the context menu, and `exportPage.js`.
  - `render/`: the render kit (HarfBuzz, fonts) and `glyphPaint.js`, which must mirror `scenePdfRenderer.paintText`.
  - `window.__cerEditor` (dev builds, or `localStorage['cer:debug']`) exposes the store and stage for tests.
- **`utils/templateMetadata.js`** and **`data/presets.js`**: template presets and metadata normalization shared with the backend.

## Key Architectural Patterns

### Storage abstraction

The active storage is chosen in `backend/src/storage/index.js`:

```js
activeStorage = shouldUseMysql() ? createMysqlStorage() : createFileStorage();
```

All storage implementations expose the same async interface: `getMode`, `getBranding`, `updateBranding`, `listStudents`, `addStudents`, `updateStudent`, `deleteStudent`, `listTemplates`, `createTemplate`, `updateTemplate`, `deleteTemplate`, `findUserByCredentials`, plus generic records: `listRecords(collection, { ownerId })`, `getRecord`, `putRecord`, `putRecords`, `deleteRecord`. Records hold template versions (`templateVersions`, owned by a template), `assets`, `jobs`, `certificates` (serials) and `counters`. MySQL keeps them in one `records` table; JSON storage in `data/records/`.

### Authentication

- Login endpoint (`POST /api/auth/login`) verifies username/password against storage and returns a signed HMAC token.
- Token secret comes from `AUTH_TOKEN_SECRET`; tokens expire after 12 hours.
- Middleware `backend/src/middleware/auth.js` validates the `Authorization: Bearer <token>` header.
- Frontend stores the token in `localStorage` and attaches it via an Axios interceptor.

### Template model

A template is a JSON object with (schema v3):

```js
{
  schemaVersion: 3,
  id, name, orientation, width, height, version,          // version: optimistic-concurrency counter
  background: { type, color, fill? /* paint */, accentColor, imagePath?, imageOpacity?, customLayout?, missing? },
  page: { margins: { top, right, bottom, left }, bleed },  // guides only
  digits: 'arabic'|'latin'|'keep',
  category?, favorite?, starterId?, paletteKey?, verification?: { enabled },
  elements: [ /* see below */ ],
  detailLevel, audienceType,
  availableBackgroundVariants? /* computed by backend */
}
```

Paints (`fill`) are a colour, `null`, or `{ type: 'linear', angle, stops }` / `{ type: 'radial', stops }`.
Elements share `id, type, name?, x, y, width, height?, rotation (around the origin), opacity, locked, visible, groupId?`.

Element types supported by the renderer:

- `text` — static text.
- `dynamicText` — text rendered from a student or branding field. Field names include `studentName`, `date`, `dateLabel`, `issueDate`, `recitalType`, `surahRange`, `programName`, `calendar`, `mistakesCount`, `teacherName`, `schoolName`, `recipientTitle`, `recipientAchievementSentence`.
- `dateField` — Hijri or Gregorian date (`date: { calendar, style, source }`).
- Text options: `fill` paint, `textDecoration` (underline/line-through), `align` (incl. justify), `verticalAlign` with `height`,
  `kashida` (0–4), `autoFit`, `effects: { shadow, outline, highlight }`. Static text may contain `{{fields}}`.
- `image` — static image (uploads path, never base64); `frame` — image masked to a shape;
  `dynamicImage` — `logo`, `signature`, or `stamp`. Images: `fit`, `crop`, `flipX/Y`, `filters`, `cornerRadius`, `border`.
- `rect`, `circle`, `polygon`, `star`, `shape` (ribbon, banner, shield…), `line` (dash, cap, start/end heads).
- `ornament` — Islamic frames, corners, borders, rosettes, arches, dividers (`shared/assets/ornaments.js`).
- `icon` — lucide icon stored as paths (`paths`), so the backend needs no icon library.
- `qrcode` / `barcode` — value template, e.g. `{{verifyUrl}}` / `{{serial}}`.

Templates without `schemaVersion` are v1. `shared/model/migrations.js#migrateTemplate()` upgrades them. It is pure and idempotent, never drops data, and makes explicit the defaults v1 printed: null fills, `autoFit` shrink on text, and legacy background decoration as elements. MySQL keeps non-column fields such as `schemaVersion` in `templates.extra_json`. Add a new migration step, not ad-hoc defaults, when the model changes.

### Arabic only

There is no i18n layer: every UI string lives in `frontend/src/strings.ar.js` (field labels in `FIELD_LABELS`). The
whole app is RTL (`<html dir="rtl">`, Radix `DirectionProvider`); use logical classes (`ps-`, `pe-`, `start-`, `end-`).
Teachers see field tokens by their Arabic labels (`editor/model/fieldTokens.js`); templates store keys.

### Template detail level and audience

- `detailLevel`: inferred from elements — if any dynamic text uses `recitalType`, `surahRange`, `programName`, `calendar`, `mistakesCount`, or `teacherName`, the template is `detailed`; otherwise `simple`.
- `audienceType`: `student` or `adult`.
- They are filters in the gallery and the wizard; any template works with any student list (`/generate-simple` now redirects to `/generate`).

### Managed background variants

The `itqan-template-5-*` family is treated specially:

- Base templates: `itqan-template-5-students` and `itqan-template-5-adults`.
- Color variants are derived from PNG files named `uploads/itqan-template-5-<key>.png` (e.g. `emerald`, `mocha`, `turquoise`).
- `backend/src/utils/templateVariants.js` collapses these into a single canonical template with `availableBackgroundVariants`.
- The frontend lets the user pick a variant; the backend applies it when generating PDFs.

If a color PNG is missing, that color is not offered.

### PDF rendering notes

- The editor and the PDF share one layout engine (`shared/render/textEngine.js`): HarfBuzz shaping, UAX #9 bidi, greedy wrap, shrink-to-fit, and Konva's baseline model. Both paint the display list from `shared/render/scene.js`. See `docs/AUDIT.md` §7 for why this was chosen over headless Chromium (Hostinger compatibility).
- Fonts are the union of `backend/assets/fonts` (bundled) and `FONTS_DIR` / `PERSISTENT_STORAGE_DIR/fonts` (uploads), for listing, `/assets/fonts` and rendering. `shared/render/fonts.js` resolves `fontFamily` + `fontStyle` to a file the same way on both sides, synthesizing bold or italic when no such face exists. Characters missing from a font fall back to Amiri, Cairo or Alexandria.
- Background images are resolved through `resolveBackendAssetPath`.
- For a single student the response is a PDF; for multiple students it is a ZIP archive containing one PDF per student.

## Deployment

### Hostinger (recommended)

1. Create a MySQL database and user.
2. Upload the project preserving `backend/`, `frontend/`, and `package.json`.
3. Install dependencies: `npm --prefix backend install && npm --prefix frontend install`.
4. Set environment variables (`PORT`, `AUTH_TOKEN_SECRET`, MySQL credentials, `VITE_API_BASE=/api`, `PERSISTENT_STORAGE_DIR`).
5. Build: `npm run build`.
6. Start: `npm start`.
7. Verify `/api/health` returns `{"status":"ok","storage":"mysql"}`.

If the host requires a separate `public_html` folder:

```bash
PUBLIC_HTML_DIR=/path/to/public_html npm run build:public-html
```

This script clears the target folder except `.htaccess` and `.well-known`, then copies `frontend/dist` contents.

### Local / no-DB quick start

Without MySQL env variables the app uses JSON files in `backend/data` and `backend/uploads`. Default users are seeded from `backend/data/users.json`.

### File persistence on ephemeral hosts

On Render or similar platforms, set `PERSISTENT_STORAGE_DIR` to a mounted persistent disk. Otherwise uploaded files and JSON data will be lost on redeploy.

## Security Considerations

- **Auth token secret**: set a strong random `AUTH_TOKEN_SECRET` in production. The default local secret is not safe for production.
- **Passwords**: stored in plain text in the JSON seed files and MySQL `users` table. Do not use real user passwords.
- **Upload validation**: images are restricted to common image MIME types and extensions; spreadsheets must look like Excel/CSV; fonts must be `.ttf` or `.otf`.
- **Static files**: `/uploads` and `/assets/fonts` are served publicly.
- **CORS**: currently permissive (`cors()` with exposed headers). Review for production.
- **File paths**: uploaded file names are sanitized and images get UUID names; fonts keep a sanitized original base name with collision handling.
- **Secrets in Git**: `.env` files are ignored. Never commit credentials.

## Code Style Guidelines

- **Backend**: CommonJS (`require`/`module.exports`), `snake_case` only for MySQL column names, otherwise `camelCase`.
- **Frontend**: ES modules (`import`/`export`), React functional components, Tailwind utility-first CSS.
- **Language**: UI text and user-facing labels are in Arabic. Code comments and internal names are in English.
- **Indentation**: 2 spaces in both workspaces.
- **Linting**: ESLint configured in `frontend/eslint.config.js` for JS/JSX; backend has no lint script.

## Common Gotchas

- The frontend dev server reads env from the project root (`vite.config.js: envDir: '..'`) so `VITE_API_BASE` must be in root `.env`, not `frontend/.env`.
- If `VITE_API_BASE` does not end with `/api`, the client appends it.
- MySQL storage auto-creates tables and seeds empty tables from `backend/data/*.json` on first startup. It does **not** overwrite existing data.
- The `itqan-template-5` color variants depend on PNG files in the uploads directory. Adding a new color means adding `uploads/itqan-template-5-<key>.png` and also adding the color to `COLOR_VARIANTS` in `backend/src/utils/templateVariants.js`.
- PDF font resolution tries exact file names first, then normalized matches, then system fallbacks. Font file names matter.
- Default branding assets (when no logo, signature or stamp is uploaded) come from `frontend/public/assets/` (`logo.png`, `signture.png`, `stamp.png`), in both the editor and the PDF.
- Template metadata (recipient titles, gender, display names) lives once in `shared/model/templateMetadata.js`; `frontend/src/utils/templateMetadata.js` re-exports it and the backend loads it with `loadModel()`. A student's `gender` overrides the "ة" heuristic.
- macOS file systems are case-insensitive: never put `galleryFilters.js` next to `GalleryFilters.jsx` (Vite resolves `.js` first).
- Uploaded files are gitignored except built-in assets listed in `.gitignore` (`itqan-template-5-*.png`, `itqan-bg-*.png`, `itqan-frame-*.jpg`).
